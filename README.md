# Lending Club 信贷风险分析

用 **Lending Club 12 年、226 万笔、340 亿美元**真实放款账本，回答信贷业务的核心问题：
**这笔生意赚不赚钱，以及我们到底是靠什么判断的。**

| | |
|---|---|
| 数据来源 | Lending Club 官方 LoanStats（2007–2018，16 个按季/半年切分的文件） |
| 数据规模 | **226 万笔**放款、**340 亿美元**本金 |
| 数据快照日 | 2022-08-31（**实测确定**，判据写在 `code/db.py`） |
| 主要工具 | **DuckDB + SQL**（取数）、Python（统计检验 / 画图） |
| 产出 | 5 组 SQL、13 张结论图、6 篇分析文档、五屏看板数据源与成品 |

## 一、三次「听起来很对、数据不支持」的结论反转

| 常识 | 数据说的 |
|---|---|
| ① **长期限（5 年）风险更高** | 60 期的 24 期违约率看着高 1.4~1.7 倍，但**拉平信用等级构成后，差异的 117% 来自构成**，剩下的方向还反了（10.09% vs 10.92%）。**期限影响的不是违约概率，而是违约损失率**——同样第 24 个月违约，36 期已还掉三分之二本金，60 期才还掉四成 |
| ② **高危等级定价不足** | 恰恰相反。**B 级风险涨了、利率一分没涨**（缺口 −0.74pp），C 级轻微不足；而 **E / F / G 的利率反而推得过头了**（G 级 +3.23pp）。根因是**反应式定价**——只有恶化到刺眼才调价，中间那些「温和恶化」的等级一直带着小缺口放款，**而它们的盘子最大** |
| ③ **IV 低 = 可以丢掉** | 借款用途 IV 只有 0.0202（弱），按机械规则该丢。但它和等级交叉后：**同一等级组内最差和最好的用途仍差 6~16 个百分点，排序在三组里完全一致**。它是**等级的放大器**，也是唯一一条能改善 A 级客户内部定价的线索 |

> 前两次反转都是「把第三个变量拉进来」造成的：一次是把假结论拆掉（期限），
> 一次是把真结论捞回来（用途）。**两次都不是靠更复杂的模型，都是靠多切一刀看看。**

## 二、分析主线（C1–C5）

| 步 | 干什么 | 一句话结论 |
|---|---|---|
| C1 | 数据认识与口径 | 快照日实测反推（否则整条账龄横轴错位）；发现 3,032 笔「已结清」实际损失本金 |
| C2 | **放款质量趋势** | 固定账龄后趋势是**倒 U 形**（谷底 2010Q1 8.29% → 2016Q3 见顶 14.22%）；效应拆解证明**恶化来自等级内部** |
| C3 | **定价与收益** | 定价缺口必须按 **LGD 折算**（实测 0.55），不折算七个等级全是负缺口、结论会反 |
| C4 | **分群与统计检验** | 18 个字段里**只有信用等级越过 0.30**（IV 0.3966，第二名 0.0468）；但 17 个字段「显著」不等于有用 |
| C5 | **行动建议** | 三条建议换算成「缺口 × 敞口 = 年化金额」：量级约 **1 亿美元 / 年**，占本金 **0.38%** |

### 三条行动建议

| # | 建议 | 年化缺口 | 敞口 | 能动手的地方 |
|---|---|---|---|---|
| 1 | **B / C 级补价** | 约 2,145 万 | 43.4 亿 | 利率矩阵（未来放款） |
| 2 | **60 期加期限价** | 约 9,615 万 | 55.0 亿 | 利率矩阵 / 准入规则 |
| 3 | **借款用途纳入规则** | 约 995 万 | 4.1 亿 | 定价与额度规则 |

> ⚠️ 三条的敞口有重叠，**简单相加是重复计算**，对外只能说「合计量级约 1 亿美元」。
> 换个口径看：占全部本金 0.38%——**这个数不大，正是它可信的理由**。
>
> 另外：只给**基期值**和方向，不给目标值。涨价之后客群会变、竞争反应会变，
> 「应该涨到多少」算不出来，那要靠真实数据反馈来调。

## 三、口径与局限（读结论前请先看这一节）

- **快照日是实测反推的**，不是猜的：仍未结清的贷款集体停在哪个月，数据就封存在哪个月。
  判据写在 `code/db.py`。
- **有一处数据集自身的坑已主动披露**：3,032 笔官方标记 `Fully Paid`（口径上算好客户）
  的贷款，本金实际从未收全，合计 **955 万美元**损失在官方口径下一分钱都没被记入，
  **方向是让 2007–2011 年显得比实际安全**，本项目改用双口径并报。
- **特征表物理隔离**：`loans_features.parquet` 只含放款前字段，
  `run_sql.py` 里有一道护栏——任何 `FROM features` 的 SQL 只要提到放款后字段就直接拒跑。
  把「记得别泄漏」从纪律变成了机制。
- **不显著 ≠ 没用，显著 ≠ 有用**：226 万笔样本下 p 值几乎全部小到打印溢出，
  所以本项目一律**以效应量（IV / Cramér's V）和置信区间作为判断依据**。
- **全是描述性分析**，不做因果推断。

完整口径、异常处理与局限声明见 [`00_口径与数据说明.md`](00_口径与数据说明.md)。

## 五、目录结构

```
├── README.md                你在这
├── 00_口径与数据说明.md      口径、快照日、异常与局限声明（读结论前先看这份）
├── 分析文档\                 01..06，一节一篇

├── data\                     ★ 原始数据与 parquet 都不在仓库里，见 data/README.md
├── sql\                      sql_01..05，DuckDB 直接跑
├── code\                     建库 / 统计检验 / 画图 / 看板
│   ├── db.py                数据库连接 + 路径 + 快照日常量
│   ├── run_sql.py           批量跑 sql/，含防泄漏护栏
│   ├── 04_segment_stats.py  唯一需要 Python 的统计计算：IV / 卡方 / Cramér's V / Wilson / 时间分半
│   └── 07_build_dashboard.py 生成五屏看板成品
└── output\
    ├── charts\              13 张结论图 + 五屏截图
    ├── tables\              各步 SQL 的结果集 + 统计检验结果
    ├── tableau\             9 张看板聚合数据源
    └── dashboard\           五屏看板 HTML 成品
```

**命名的步骤前缀用 C**（Credit），和淘宝项目的 **S**（Shop）区分开。
